# AI DevOps Assistant — Agent Instructions

## Project Goal
Build a privacy-first, production-oriented AI DevOps assistant that investigates incidents using local LLM inference, read-only diagnostics, evidence correlation, and runbook retrieval.

## Current Branch
Primary development branch: `feature/agentic_ai`

## Engineering Rules
- Keep the core MVP small and production-oriented.
- Prefer deterministic, testable Python code over unnecessary abstractions.
- Preserve the read-only safety boundary for diagnostic tools.
- Never add destructive Kubernetes actions without an explicit human-approval design.
- Never hard-code secrets, tokens, credentials, or local model files.
- Treat tool output as evidence; clearly distinguish observations from inference.
- Normalize LLM output before returning API responses.
- Keep FastAPI/Pydantic response contracts stable.
- Add or update tests when changing agent behavior.

## Agent Investigation Flow
1. Receive service, namespace, and incident question.
2. Ask the local LLM for the next diagnostic action.
3. Validate the requested action against the registered tool set.
4. Execute only registered read-only tools.
5. Accumulate successful diagnostic evidence.
6. Stop early when sufficient core evidence exists.
7. Collect required telemetry when the question requires metrics/correlation.
8. Retrieve relevant local runbooks.
9. Synthesize a final RCA from collected evidence.
10. Normalize evidence/actions and validate the API response.

## Evidence Standard
Core Kubernetes evidence normally includes:
- Pod status
- Pod logs
- Kubernetes events

For telemetry-focused investigations, also collect:
- Service metrics
- Error rate
- P95 latency

Do not claim a root cause that is unsupported by collected evidence.

## Testing
Run before committing:

```powershell
pytest -q
```

A change is considered ready only when the full test suite passes.

## Repository Hygiene
- Keep `.venv`, caches, `.env`, and GGUF model files out of Git.
- Keep documentation synchronized with the actual implementation.
- Use focused commit messages such as `docs: update agentic investigation flow`.
- Avoid committing generated logs, temporary files, or editor metadata.

## Documentation
The README should explain the current working system first, then the roadmap. Do not describe planned features as implemented features.

## Demo Safety
The current Kubernetes and Prometheus integrations may use mock data for local development. Clearly label mock/demo telemetry so it is not confused with a live cluster integration.
